## 一、必须先纠正的一条结论（上个提交自认"未验证通过"）

`8a4880c` 自述：改用 `--spring.profiles.active=dev,prod` 后 `/v3/api-docs` 仍然 200，
因此判定 `allMatch` 改动无效、阶段 0.1 不能算完成。

**实测（用该提交自己构建的 jar，两方独立复现）：**

| 场景 | `/v3/api-docs` | `/swagger-ui/index.html` | `/api/v1/categories` |
|---|---|---|---|
| `dev` | **200** | 200 | 200 |
| `dev,prod` + 注入 `PLATFORM_*` | **401** | **401** | 200 |
| `dev,prod` 未注入密钥 | 应用**拒绝启动**（`StartupSecretGuard`） | — | — |

⇒ **gating 代码是对的。** 那次看到 200 的原因：`dev,prod` 的实例**根本没起来**
（缺生产密钥时守卫必然拒绝），回答 200 的是**残留在端口上的 `dev` 实例**。

**教训（比这条结论本身更重要）**：验证 profile 门控时，必须能证明**是哪个进程在回答**
（PID / 端口占用 / 启动日志）。否则"旧进程答新问题"会让任何安全结论反向。
现在这条已由 `SwaggerNotPublicOutsideDevTest` 自动守着 —— 阶段 0.1 之所以"改了却无法证明"，
根因不是代码，而是**缺这条断言**。

## 三、故意未修：需要先定口径（⛔ 不要照抄"最佳实践"直接改）

### 1. `task.escrow_amount` 没有任何写入方（**最严重的剩余项**）

- 事实：全仓 10 处引用**全是 SELECT**，无 INSERT/UPDATE、无触发器、无生成列；
  设计文档 `:4112`/`:4164` 把它定义为**冗余展示列**（列表页展示托管状态）。
- 后果一：`EscrowService:113-118` 用它做"应付 == 实付"严格校验 ⇒ 恒为 `0.00`
  ⇒ 任何非零付款都抛 `AMOUNT_MISMATCH` ⇒ **托管在真实链路下不可能成功**。
- 后果二：`AwardService:119` 的 `if (escrow > 0 && ...)` 超发拦截**整段被短路**。
- 为什么测试是绿的：5 个测试类在 fixture 里**手工 INSERT 了 `escrow_amount`**。
- **待定口径**：它到底是
  (a) 冗余展示列（那资金路径必须改读权威事实源：`escrow.amount` / `biz_order.total_amount` / `task.price`），还是
  (b) 发布时写定的应付金额（那 `TaskCommandService` 必须写它，且 FIXED / BIDDING 两种发单模式取值不同）？
  ⇒ 两种改法的业务语义不同，**必须由设计文档作者拍板**，⛔ 不能由实现者猜。

### 2. 抽成引擎整体缺失

`commission_detail` 在**生产代码里 0 处引用**，`SettlementService.doReleaseShare` 把
`share_amount` **全额**放给接单方 ⇒ 佣金恒为 0。
设计文档 `:1288-1290` 的权威算法是「只算佣金，实得用减法」，
库层 `ck_comm_balanced`（佣金+实得=基数）也已就位。
⚠️ 但这是**功能**不是缺陷修复（要落费率规则查找 / min_fee / 公益 0% 白名单 / rule_snapshot），
且 `AcceptanceServiceTest:151-153` 现断言"接单方拿到全额"——
**实现佣金的那一刻这条测试必须一起改**。

### 3. 审核链路的守卫条件（不变量只在注释里）

`TaskAuditService.fire` 接受任意事件名 + 调用方传入的 `operatorId`，
且**从不与 `task.publisher_id` 比较**（可自审）；
`fire("ESCROW_PAID_GRAB")` 能让未托管任务直接上线。
设计 §4.11.4 的"守卫条件"列**一处都没有实现**。
⚠️ 缓解事实：这些链路**目前没有任何 controller**（全仓 7 个 controller、1 个 `@PreAuthorize`），
HTTP 层触达不到；**落地第一个 controller 时必须一起补**，否则会立刻暴露。

### 4. 哈希链检不出"截断"

删段内最后一行 / 删整段 / 改 `created_at` 移出 48h 窗口，校验全部通过。
需要新增段封存表（`table_name, chain_hour, row_count, tail_hash`）并让 `ChainVerifyJob`
遍历封存表而不是遍历现存数据 ⇒ 属于**新功能 + 新迁移**。

### 5. `@Audit` 全工程 0 次使用 ⇒ `sys_audit_log` 在生产恒为空

改岗位（含 `permission_version+1` 的**提权动作**）、实名审核结论目前**零审计**。
需要给高危动作逐个补注解 + 补 `operatorRole`（切面从不设置它，`snapshot()` 也从未被读取）。
⚠️ 与第 3 条同源：**先定"哪些动作必须审计"的清单**，再补注解。

### 6. 其他已知但未动（各自独立）

- `escrow_share` / `delivery_unit` 缺唯一键 ⇒ DDL 自称的「Σ份额 == 托管额」库层零强制；
  一旦出现两条份额，分账配平校验必然失败、**钱卡死在托管池**。
- `sys_real_name.id_card_hash` 非唯一（而 `phone_hash` 是 UNIQUE）⇒ 一人多号 TOCTOU。
- 枚举列 CHECK 覆盖不一致（`task.status` / `sub_order.status` / `wallet_txn.biz_type` 都没有）；
  `wallet_txn` 的 direction 全仓恒为 CREDIT，DDL 声称的"Σ借=Σ贷"永远不成立。
- `escrow.channel_order_no`（每次回调全表扫）、`sub_order.task_id`（驳回热路径全表扫）缺索引。
- 前端三端**没有任何类型检查闸门**（无 `vue-tsc`、无 `typecheck` 脚本、CI 无前端 job）；
  `mobile` 的 API 基地址硬编码 `127.0.0.1`（已编进小程序产物）。
- `Spring Boot 3.2.5`（2024-04）：按项目时间点（2026-10）已远超 OSS 支持窗口，不再收安全补丁 —— 建议排期升级。
- 手写 TS 类型与 `openapi.yaml` 已存在真实漂移（`PageResult` 的 `total/pageNum/pageSize`、
  `TaskSummary` 金额 `string` vs `BigDecimal`），且**没有任何探测器**。
