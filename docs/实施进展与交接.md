## 3. ⭐ 本会话反复踩到的缺陷类别（按出现次数）

| # | 类别 | 出现次数 | 收敛点 |
|---|---|---|---|
| 1 | **`NOT NULL DEFAULT x` 的列插入显式 null → 1048** | **12 次** | `common/db/RowValues`（主表只插有值的列；子表 `nz()` 归一） |
| 2 | **JSON 列不能用普通字符串 / 往返不一致** | 3 次 | `RowValues.toJson`；参与哈希的值必须取「取回后」的形态 |
| 3 | **测试之间通过持久状态互相污染** | 5 次 | Redis 限流计数 / 撞车身份证号 / 随机 IP / 钱包余额 —— 一律加 `@BeforeEach` 重置或独占分段 |
| 4 | **随机值空间太小 + 无重试** | 2 次 | `user_no`(T10) / `task_no`(T15)。⭐ 重试只能兜住偶发碰撞；**空间不足时碰撞是必然**，要加长空间 |
| 5 | **自建父 pom 丢失框架默认值** | 2 次 | `repackage` 绑定、`-parameters` |
| 6 | **异常兜底把 HTTP 语义吃掉** | 2 次 | `AccessDeniedException`→200(T6)、`NoResourceFoundException`→200(本轮)。均已加显式处理器 |
| 7 | ⭐ **用脚本改代码，改了但没生效，却打印了成功** | 4 次 | 见下节 |

### 第 7 类最危险，单列出来

四次的实际形态：

1. `.replaceAll('"PENDING"', '"QUOTED"')` —— SQL 里是**单引号**，只改到了 Java 字符串
2. `putIfPresent` 的正则写了 `String column`，文件里实际是 **`String col`**
3. 锚点 `/** null → 空串。` 没命中，**`toJson` 的定义没加上**，但调用点加上了 ——
   **增量编译没报错**（旧 class 还在），直到 `clean` 重建才暴露
4. 脚本因为「文件变了」就打印 ✅，而那次唯一的变化是**加了一个用不到的 import**

⛔ **规则**：用脚本改代码后，必须**逐个回读目标位置的真实内容**，
不能看脚本输出。且**改完行为没变化时，第一反应是"改动真的生效了吗"**，
而不是「再调一次参数」。

## 4. ⭐ 两条我认为最值钱的工程判断

### ① 状态机的价值不在于允许什么，而在于拒绝什么

T10 把迁移表**条数钉成断言**（`transitionCount() == 38`），实跑报 36 ——
**正是这个断言逼出了我漏掉的 2 条迁移**（文档 #3「审核通过且已托管」的两条分支，
即"发布即托管"这条主路径）。若只测「合法迁移能过」，那 2 条漏掉的永远不会被发现。

### ② 注释不是机制

`NOT NULL` 那个坑我踩了 12 次，中间在 T9、T11、T13 各写了一遍注释提醒 ——
**第 10、11、12 次照样踩**。最后是 `RowValues` 这个**代码机制**在收敛它。

> **凡是「我提醒过自己」却还在重复犯的错，就该停下来做工具，而不是再写一遍提醒。**

## 5. ⚠️ 我在已提交的代码里写错过的两处事实断言

如实记录，因为它们都**看着很合理**：

1. **「库里刻意没有钱包表、资金不过平台账户、构成二清红线」**（T16）
   —— 完全错误。`wallet_account` / `wallet_txn` / `withdraw_apply` 都在。
   **错因：探查时用了 `wallet` / `wallet_transaction` 两个不存在的表名，
   把「查不到」当成了「不存在」。**
   ⇒ 探查必须先**列出全部表**再挑，⛔ 不要凭记忆拼表名去查。

2. **「这些是公开只读接口，未登录也要能渲染」**（T8 的 `CategoryController`）
   —— 与实现不符（实际 401）。**单元测试结构上不可能发现**，
   因为它直接调 Service，绕过了 HTTP 层与鉴权。
   ⇒ 这类矛盾只有**真实启动 + 打真实接口**才能暴露。

> **结论越"漂亮"，越该回头核对依据。** 这两条我都曾当作"设计亮点"来汇报。
